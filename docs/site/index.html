01 / What it does

The tools to
trust the draft.

  1. 01

    Workflows

    Every run on one page: the stage it is on, who owns it, the state of its output and the one next action.

    Blocked, waiting and done look different at a glance. A run keeps its own frozen copy of the workflow it started with, so a template edit never changes work already in flight.

  2. 02

    Output review

    Evidence, original output, your edits and the approval state side by side.

    The evidence names each source as read, empty or missing, so a confident draft built on nothing is caught before anyone signs it.

  3. 03

    Approval gates

    Independent reviewers sign a hash of the content. The owner and the author can never approve their own stage.

    Change the content after signing and the signatures stop counting. The server enforces this, not the page, so any client that skips the interface meets the same rule.

  4. 04

    Agent Studio

    Build agents from honest templates, grant tools with call budgets and timeouts, and test them before they touch a stage.

    A saved test is bound to the agent version it was written for. An agent without a passing test on its current version cannot be assigned; the API answers 409.

  5. 05

    Connectors

    Attach a reviewed, hashed snapshot of a Jira ticket, a Confluence page or an Ontology dataset to a run.

    Evidence reads are read only and separate from configured actions such as a Jira update, a Slack message or a reviewed Lambda invocation. A public dataset enters through ontology:ingest with each source file's hash recorded.

  6. 06

    Audit package

    Any run exports as Markdown or JSON with every output, signer and hash, and verifies offline.

    corepack pnpm audit:verify file.json recomputes every hash and names each problem. A handling marking such as CUI appears on every page and on the first and last line of every package.

How a stage works

Five steps.
No shortcuts.

  1. 01

    Agent drafts

    Read only tools, a call budget, a timeout and the sources it must read.

  2. 02

    Evidence attached

    Files read, tools called, checks passed or failed, all named.

  3. 03

    Person reviews

    The draft sits beside its evidence. The owner edits the handoff.

  4. 04

    Reviewer signs

    Never the author, never the owner. The signature is over a content hash.

  5. 05

    Stage locks

    The run advances and the trail stays. Edit the output and the signatures are void.

04 / Engineering

One policy boundary.
Many ways to work.

The browser presents state. The server decides what may happen. MCP clients reach the same workspace engines through scoped tools.

Browser / MCP→Identity + schema→Workflow engine→Evidence + review
TypeScript / ESMNode 22React + HTML/CSSZodMCP SDKesbuildJSON persistence
Follow a real request through the code
  1. browser.ts renders the workspace and submits an action to the HTTP API.
  2. server.ts resolves identity, verifies workspace membership and validates the payload.
  3. pipeline.ts checks the run revision, stage, role and approval rules before updating state.
  4. scheduler.ts runs approved assistant stages with saved references. Local repository agents use bot-worker.ts with explicit tool policies.
  5. storage.ts persists workspace state. Drafts, evidence and content hashes remain available for review.
05 / Company security

The right access.
At every handoff.

Choose a company, assemble its agents into a workflow, then check the configuration before handoff. Select a stage to see the application control and its proposed AWS protection.

Company + team→Tools + agents→Workflow + controls→Review + readiness

Illustrative control walkthrough. No authentication, AWS request or security test runs here. AWS protections require deployment and validation; they are not active in this local preview.

Before a company goes live
  1. Review agent assignments, model choices, references, tool permissions and execution limits. Current workflow checks report blockers; they do not deploy infrastructure.
  2. Separate production and development accounts; scope operator, worker and deployment roles.
  3. Test tenant isolation, denied tools, provider destinations and independent approvals.
  4. Review vulnerabilities, rehearse incident containment and restore a workspace from backup.
  5. Agree on data retention, region and provider use. Cloud hosting alone does not establish compliance.

06 / Questions

A few things
worth knowing.

Does it send my documents anywhere?

Model requests and configured external actions can send selected content outside the workspace. Review references, provider settings and message previews before sending. Nothing leaves the machine on its own.

Can an agent publish or deploy on its own?

No. Agents receive no deployment rights. Approval gates and integration permissions are checked by the backend, and configured external actions are separate from drafting.

Which models work?

Installed Ollama models and supported provider integrations with valid credentials. Saved connections use server side settings or the encrypted vault. Credentials are referenced by setting name and never stored by Magentic.

What happens when something is not set up?

You get the setup steps on the page. Not connected, not assigned, blocked and waiting each show the one action that resolves them.

Is this a compliance claim?

No. The federal readiness map shows which behaviours support which control families and names the known gaps. An authorization decision belongs to the agency and its assessors.

Current limits

  • This website simulates the journey; it is not an authenticated workspace.
  • Model completion and token counts do not establish answer accuracy. Review the cited evidence.
  • Company repository execution needs isolated workers before it can be enabled.
  • File backed company storage assumes one writer. Hosted scale, backup and recovery need further work.
  • Clerk, Stripe, Slack, Jira, Lambda and Foundry require real configuration. This page connects none of them.
  • No claim of federal authorization, accreditation or production readiness.
